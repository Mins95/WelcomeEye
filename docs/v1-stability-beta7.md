# WelcomeEye Connect V1 stability — beta 7

This note records the evidence, fixes and validation limits for `0.3.1-beta.7`.

## Scope

Beta 7 is a stability release for the existing V1 `16/1/2` media/control path. It does not introduce a new output command, a new doorbell path or a second socket reader. Connect 2 behavior remains unchanged.

The release addresses faults observed on Home Assistant 2026.9.x / Python 3.14 and failure modes capable of closing a V1 media session while an output command is waiting for confirmation.

## Evidence from real diagnostics

### Home Assistant / WebRTC mDNS

A real Home Assistant log reported blocking imports from `dns.rdata.get_rdata_class()` for:

- `dns.rdtypes.CLASS32769.SRV`
- fallback `dns.rdtypes.ANY.SRV`

The class value `32769` is `IN | 0x8000`, the cache-flush class used by mDNS. Beta 6 loaded dnspython record implementations in Home Assistant's executor, but did not populate the exact `32769` class cache used by aioice. Therefore a later mDNS packet could still trigger a dynamic module import on the Home Assistant event loop.

### H.264 decoder failure

A real V1 session reported PyAV/FFmpeg `InvalidDataError` from H.264 decoding (`avcodec_send_packet()` / `no frame`). Before beta 7 this exception escaped `MediaPipeline.feed_video()` and was treated by the hub as a media-connection failure. That closed the V1 session even though the TCP transport itself had not necessarily failed.

### Output command waiting for TLV 506

Tester diagnostics from beta 6 showed:

- V1 profile `16/1/2` selected successfully;
- Start AV request and positive Start AV response;
- 24 Annex-B H.264 packets observed;
- one output command accepted;
- `request_send_attempt_count = 1`;
- `request_sent_count = 1`;
- no TLV 506 response observed;
- command failure at `waiting_confirmation` because the media session closed;
- later connection attempts encountered a refused cached endpoint and then a discovery timeout.

This proves that beta 6 reached the single TLV 505 send. It does **not** prove why that session closed. Two software paths were identified that could close the same session before confirmation: an H.264 `InvalidDataError`, and a completely clean V1 media-header timeout while the device temporarily emits no media. Beta 7 removes both failure paths from the pending-output window without changing the TLV 505 packet or adding a retry.

## Beta 7 changes

### Exact mDNS-class preload

Startup still performs DNS preloading through `hass.async_add_executor_job()` before the hub or camera platform is created. In addition to `load_all_types(disable_dynamic_load=False)`, beta 7 resolves every known `RdataType` against the exact mDNS class `1 | 0x8000` while still in the executor.

This warms dnspython's class/type cache before aioice can receive an mDNS datagram on the event loop. Dynamic loading is not disabled globally.

### H.264 decoder recovery

`MediaPipeline.feed_video()` now treats only `av.InvalidDataError` as recoverable media corruption:

1. the invalid H.264 access unit is dropped;
2. the H.264 decoder context is recreated;
3. dependent P frames are discarded locally;
4. decoding resumes only from a later V1 I/key frame;
5. the TCP/media session remains open.

Unexpected exceptions are still propagated. Beta 7 does not hide arbitrary decoder, muxer or application errors. The failed H.264 packet is not muxed and does not advance the video PTS.

### Clean media idle while TLV 506 is pending

The V1 reader intentionally distinguishes an untouched OWSP header timeout from a partial-frame timeout. A partial header/payload keeps the existing bounded receive rules and is never silently discarded.

After the media worker has claimed and attempted the **single** TLV 505 send, beta 7 enables a session-local `v1_allow_idle_timeouts` guard for that exact command window. If the next V1 read times out before receiving any byte of a new OWSP header, `Session.read()` returns an empty batch instead of declaring the authenticated session dead. The worker then continues reading the same socket, allowing a delayed video frame or TLV 506 to arrive.

The guard is disabled as soon as the command is confirmed, fails, times out, is cancelled or the media session closes. Outside a pending output command, normal V1 timeout behavior is unchanged. Connect 2 never enables this guard.

This is **not** a retry or reconnect. No new session is opened and no second TLV 505 can be generated by the idle handling.

### Output safety during media recovery

The output path remains the beta 5/6 architecture:

`button -> V1MediaOutput -> existing media worker -> TLV 505 -> same media worker observes TLV 506`

The media worker remains the only reader/writer for that socket. Decoder recovery and clean-idle preservation do not create a new socket, do not move a pending command to another session and do not send another TLV 505.

If the original media/TCP session genuinely closes after TLV 505 was sent, the result remains uncertain and the integration returns an error. It does **not** reconnect and replay the output action.

## Offline validation

The beta 7 CI matrix runs the complete suite on both Python 3.12 and Python 3.14 with PyAV 17.0.1 and dnspython 2.8.0.

The stability suite contains **101 tests plus 3 subtests** and includes:

- exact mDNS class `32769` preload without a later dynamic import;
- dynamic dnspython loading left enabled globally;
- invalid H.264 I-frame recovery;
- invalid H.264 P-frame recovery;
- P-frame discard while waiting for a fresh keyframe;
- unexpected decoder exceptions still propagating;
- V1 clean-header idle timeout preserved only during the pending-output window;
- zero-length padding followed by a clean idle timeout without poisoning the V1 reader;
- normal V1 and Connect 2 timeout behavior unchanged outside that window;
- one TLV 505 followed by a simulated H.264 decoder failure and then TLV 506 on the same session;
- the actual V1 hub media worker with real PyAV decoding, an injected decoder failure after the command send, recovery on a fresh keyframe and a later TLV 506 confirmation;
- the previous no-retry, stale-confirmation, partial-send, reconnect, UID/profile and Connect 2 regressions.

HACS and Hassfest validation are also required to be green before publication.

## Safety invariants

These rules remain non-negotiable:

- one accepted strike/gate action permits at most one TLV 505 send attempt;
- a sent or partially sent command is never retried automatically;
- a pending command is never transferred to a replacement media session;
- a missing/late TLV 506 is not treated as proof that the relay did or did not move;
- pre-login discovery/TCP recovery may occur only before an output packet exists;
- no brute-force protocol variants are sent to hardware.

## Hardware validation still required

Beta 7 is software-validated but the tester must still confirm the real V1 behavior. Use one deliberate action at a time:

1. verify live video starts and remains stable;
2. perform one door-strike action only;
3. verify whether the relay moves physically;
4. confirm video remains available after the action;
5. close the Home Assistant view and verify the official application can obtain preview again;
6. test the gate separately only after the strike result is understood.

Do not repeat an output action automatically after an error or uncertain result.

## Doorbell

V1 doorbell support remains on standby. Beta 7 does not change the conclusions in `v1-doorbell-beta6.md`: a cloud push path is proven in the official application, while a complete reliable local V1 subscription/event path is still not established.
